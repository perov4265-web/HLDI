# Протокол обмена HLDI

Это бинарный протокол обмена между программой для ПК и прошивкой контроллера по
последовательному каналу (USART1 на контроллере, по умолчанию 115200 8N1, либо
921600 в высокоскоростной сборке прошивки). Он задан заголовком прошивки
`firmware/HLDI_Firmware/hldi_protocol.h` (портирован из оригинального `hldi.h`
автора AlphaCrow) и реализован одинаково с обеих сторон:

* прошивка: `hldi_proto.h` (`HldiProto::feed` / `send_block`);
* ПК: `pc-software/hldi/core/protocol.py` (`Packet.decode` / `Packet.encode`).

Обе реализации проверены на побайтовую совместимость.

## Формат кадра

```
+--------+--------+===========+--------+--------+--------+--------+
| CBEG   | CID    |  PAYLOAD  | LEN    | KS lo  | KS hi  | CEND   |
+--------+--------+===========+--------+--------+--------+--------+
  0xD6     id        n байт     n+6     контр. сумма (16)  0xE7
```

* `CBEG` = `0xD6`, `CEND` = `0xE7`.
* `CID` — идентификатор команды (см. таблицу).
* `PAYLOAD` — `n` байт; для команд со значением первые 4 байта — это
  знаковый 32-битный аргумент в порядке little-endian (`prm`).
* `LEN` — `n + 6` (полный размер кадра, включая заголовок и хвост).
* `KS` — `(CBEG + CID + LEN + сумма(PAYLOAD)) & 0xFFFF`, little-endian.

Важно: байт длины передаётся **после** полезной нагрузки, а не перед ней. Это
особенность оригинальной функции прошивки `SendBlock`, и обе стороны её
соблюдают.

Ответ использует тот же формат кадра; `ACK` — это просто пустой кадр `CMD_ACK`:
`D6 00 06 DC 00 E7`.

## Команды

| ID | Имя       | Аргумент (`prm`)             | Действие |
|----|-----------|------------------------------|----------|
| 0  | CMD_ACK   | —                            | квитанция / пинг |
| 1  | CMD_INFO  | —                            | вернуть блок `MCUINFO` (указатели буферов + версия) |
| 2  | CMD_CONF  | —                            | применить блок `CONFIG`, находящийся в ОЗУ |
| 3  | CMD_BOOT  | —                            | перезагрузка (вход в обновление прошивки) |
| 4  | CMD_READ  | адрес; payload[1]=длина      | прочитать блок ОЗУ в ПК |
| 5  | CMD_WRITE | адрес; payload=байты         | записать блок ОЗУ из ПК |
| 6  | CMD_MVS   | —                            | остановить движение |
| 7  | CMD_MVX   | позиция, мкм                 | переместить каретку в абсолютную X |
| 8  | CMD_MVY   | позиция, мкм                 | переместить стол в абсолютную Y |
| 9  | CMD_STX   | шаги                         | сместить каретку на N шагов энкодера |
| 10 | CMD_STY   | шаги                         | сместить стол на N шагов двигателя |
| 11 | CMD_SPX   | скорость                     | задать скорость каретки |
| 12 | CMD_SPY   | скорость                     | задать скорость стола |
| 13 | CMD_LSR   | уровень                      | лазер: >0 мощность, 0 выкл, <0 засветка из ОЗУ |
| 14 | CMD_LPTR  | адрес                        | задать указатель активного буфера засветки |
| 15 | CMD_AXSX  | позиция, мкм                 | задать координату каретки X |
| 16 | CMD_AXSY  | позиция, мкм                 | задать координату стола Y |
| 17 | CMD_DBG   | режим                        | вкл/выкл захват отладочных данных |

## Чтение позиции установки

Позиция не передаётся сама по себе. ПК читает её так, как её предоставляет
прошивка:

1. `CMD_INFO` → возвращает `MCUINFO` с адресом статусного блока `SINFO`.
2. `CMD_READ` по этому адресу, длина 16 → `SINFO { int dx; int dy; int sp;
   uint state; }`, где `dx`/`dy` — позиции каретки/стола в шагах, а биты 0/1
   поля `state` — флаги движения.

## Преобразование единицы ↔ шаг

Обе стороны используют одну формулу (в прошивке `CalcStepX/Y`, на ПК
`MotionConfig`):

```
шаги = (поз_мкм * разрешение * 2 / единица + знак) / 2     // с округлением
```

где `разрешение`/`единица` берутся из блока `CONFIG`: каретка
`rsx=600, unx=25400` (600 dpi), стол `rsy=400, uny=1000` (400 шагов/мм).

## Беспроводная связь и обнаружение устройства (ESP32)

Прошивка ESP32 передаёт **тот же бинарный протокол** поверх WiFi и Bluetooth и
добавляет автоматическое обнаружение. Константы заданы в
`firmware/HLDI_Firmware_ESP32/hldi_discovery.h` и продублированы в
`pc-software/hldi/hardware/discovery.py`.

### Обнаружение по WiFi (UDP-маяк)

* ПК рассылает широковещательный запрос `HLDI?WHO` на UDP-порт **50505**.
* Каждый контроллер отвечает (отправителю), а также сам излучает маяк каждые
  ~3 с — работают и активный опрос, и пассивное прослушивание (маяк при
  широковещательном запросе).
* Маяк — одна строка JSON:

  ```json
  {"hldi":1,"name":"HLDI-3F2A","ver":36,"ip":"192.168.1.50",
   "port":3333,"mac":"AA:BB:CC:DD:EE:FF","transport":"wifi"}
  ```

* Далее команды идут по TCP-соединению на объявленный `port` (по умолчанию
  **3333**) в том же формате кадра, что описан выше.

### Обнаружение по Bluetooth LE

* Контроллер объявляет сервис с UUID
  `6e40a001-b5a3-f393-e0a9-e50e24dcca9e` и имя, начинающееся с `HLDI-`.
* Пара характеристик в стиле Nordic-UART передаёт бинарные кадры:
  RX `…a002` (ПК → устройство, запись) и TX `…a003` (устройство → ПК,
  уведомление).

### Настройка WiFi через USB

Реквизиты WiFi настраиваются по USB-порту (бинарный канал там не доступен). В
мониторе последовательного порта на 115200 бод:

```
wifi <ssid> <пароль>       задать реквизиты подключения (станция)
ap [ssid] [пароль]         включить резервную точку доступа (SoftAP)
name <имя-устройства>      задать объявляемое имя
show | save | reboot       показать | сохранить | перезагрузить
```

Реквизиты сохраняются в NVS. Прошивка держит приёмный буфер и автоматически
переподключается к WiFi при обрыве связи; бэкенды ПК аналогично пытаются
автоматически переподключиться при ошибке транспорта.
